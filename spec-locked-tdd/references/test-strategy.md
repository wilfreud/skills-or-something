# Test Strategy — Selecting the Smallest Faithful Oracle

The purpose of test selection is not to maximize the number of tests. It is to place an executable oracle at the cheapest level that can actually observe the risk.

## Unit / component behavior tests

Use when behavior is deterministic and can be exercised through a stable public surface without requiring real infrastructure.

Prefer:
- observable outputs/state changes;
- one coherent behavior per test;
- explicit Given/When/Then structure when it improves readability;
- real value objects and lightweight collaborators;
- deterministic clocks/randomness through explicit injection when relevant.

Avoid:
- private-method tests;
- tests that assert implementation call order without contractual meaning;
- reimplementing the production algorithm in the assertion;
- excessive mocking that proves only that mocks were configured correctly.

## Property-based / fuzz tests

Use when the domain has stable invariants over a large input space.

Good candidates:
- parsers/serializers and round trips;
- arithmetic/accounting conservation rules;
- state machines and transition constraints;
- ordering/idempotency/commutativity properties;
- validation boundaries;
- codecs and transformations;
- “must never panic/crash” input surfaces.

Property tests complement examples. Keep a few named examples for important business semantics.

## Integration tests

Use when correctness depends on a real technical boundary:
- SQL queries, indexes, constraints, transactions, isolation;
- ORM mappings;
- serialization/deserialization;
- filesystem behavior;
- framework routing/middleware/configuration;
- cache semantics;
- queues/brokers;
- dependency version/configuration behavior.

Mocks cannot prove these contracts.

## Contract tests

Use at a service/provider boundary when a local fake or mock may drift from the real protocol.

Validate:
- request/response shape;
- status/error semantics;
- required headers/metadata;
- schema compatibility;
- retry/idempotency assumptions;
- version compatibility.

## Acceptance / E2E tests

Use sparingly for critical cross-component journeys and user-visible outcomes.

They are useful for catching wiring/configuration problems that focused tests cannot see, but are usually slower, harder to diagnose, and more fragile. Do not make broad E2E tests the inner TDD loop.

## Smoke tests

A smoke test answers roughly: “Is the integrated system alive enough to attempt the primary path?”

Use after integration/deployment or as a fast environment sanity check. It is not a substitute for precise behavioral tests.

## Mutation testing

Use selectively when the question is: “Would these tests actually fail if the production logic were wrong?”

Especially useful for:
- critical domain rules;
- validation/authorization logic;
- deceptively high coverage;
- tests generated by an LLM;
- regression suites whose assertions may be weak.

Surviving meaningful mutants indicate missing or weak assertions, but mutation scores are not a universal quality target. Some mutants are equivalent or low-value.

## Risk-to-test mapping

| Risk | Primary test evidence |
| --- | --- |
| Pure business rule | Unit behavior tests + properties where useful |
| Invalid states | Unit/property tests + defensive assertions |
| DB constraint/transaction | Integration test against real DB engine |
| External API drift | Contract/integration test |
| Authorization | Behavior tests + integration through actual auth boundary |
| Money/accounting | Examples + invariants/property tests + persistence integration |
| State machine | Transition table examples + invariant/property tests |
| Concurrency/races | Deterministic concurrency tests + integration/stress where needed |
| Retry/idempotency | Integration tests with repeated delivery/failure injection |
| Full critical journey | Small acceptance/E2E test |
| Deployment wiring | Smoke test |

## Heuristics, not quotas

Google’s published testing guidance describes a rough test-size distribution such as many small tests, fewer medium tests, and very few large tests. Treat such ratios as heuristics, not compliance targets. The correct mix depends on where the actual failure modes live.
